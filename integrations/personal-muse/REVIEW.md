# Personal Muse reviewer and publication guide

This is a runbook, not a record of successful live tests. Record actual results, deployed commit, account entitlements, client/protocol version and dates privately. Sources: [Personal Muse guidelines](https://muse.ai/platform/docs), [connector submission portal](https://muse.ai/platform), [SimplePost MCP documentation](https://docs.simplepost.social/mcp).

## Dedicated test access

Create a dedicated **Personal Muse reviewer** SimplePost user, with a maintained active entitlement through the review period and no customer data. Do not reuse another platform's public demo credentials. Connect one controlled text-capable test social destination and a second controlled destination for multi-account error tests. Provide approved non-sensitive image/video fixtures, an existing draft, one future scheduled post and one safely published test post. For TikTok, supply an owned test account and media if that capability will be claimed.

Decide whether the submitted release includes `PLUGIN_EXTENSIONS` and `IMAGE_FITTING`; make the reviewer account's entitlements representative. Supply the matching schema profile. If extensions are not in scope, verify they are not advertised to that reviewer and disclose that separately entitled users can receive additional tools. Do not enable unreviewed tools silently after approval. Ask Meta how entitlement-based catalogs should be represented. If extensions are claimed, review every editor/settings tool and actual UI compatibility; the kit includes all 23 classifications, not just the 12 base tools.

Give Meta sign-in instructions, credentials, OAuth client secrets (if needed) and fixture access **only through its secure submission channel**. Use the normal SimplePost login flow; account connection remains in the web app. Never put secrets in GitHub, a public demo video or the generated bundle. Maintain availability and a private evidence log throughout review.

## Acceptance scenarios

Each sensitive step requires its own approval showing the exact content, media, account IDs, mode and scheduled instant. Use only controlled test accounts. Do not execute publication merely to prepare this kit.

| Scenario                       | Procedure                                                                                                                                                        | Required evidence                                                                                                                   |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Read-only connection           | Connect through OAuth; select Read only; discover accounts, inspect posts and ask for next week's schedule                                                       | Token grants account/post reads, not validation/write scopes; only the review user's data is returned                               |
| Read-only write denial         | Attempt upload, supplied-content validation/preview, create, update, discard and enabled editor/settings writes with the same grant; also attempt REST mutations | Scope error before service execution; no new media, post, working copy or settings change; no browser-cookie fallback               |
| Consent/upgrade                | Deny connection, then connect; deliberately reconnect choosing Read and write                                                                                    | Denial creates no usable grant; client honors the token's returned scope; reconnect is required for expanded access                 |
| Draft end to end               | Discover account IDs; request preview/check of exact test copy; approve `create_post` with `postingMode: draft` and a retained idempotency key; inspect drafts   | A saved draft ID and validation details; no social publication; draft may be invalid and must not be reported ready if errors exist |
| Schedule and follow-up         | Review and approve a test post for a known future ISO time with timezone; inspect schedule; separately approve a time/content change; inspect again              | Matching accounts/content/instant and status; scheduling is not reported as already published                                       |
| Cancel                         | Separately approve discarding the future test post; inspect schedules                                                                                            | Item removed/not scheduled; account/media cleanup outcome accurate; no claim of retracting a published post                         |
| Publish now                    | In a controlled test account, approve exact copy/media/destinations, then invoke `create_post` with `postingMode: now`; inspect returned per-account results     | Muse asks every invocation; actual successful result/link where available, no success claim for failed destinations                 |
| Sensitive approval repeat/deny | Repeat publish/update/discard/commit or destructive working-copy overwrite with new details; deny a confirmation                                                 | No always-allow option for sensitive tools; changed payload needs fresh approval; denied call has no side effect                    |
| Retry/duplicate handling       | Simulate an uncertain creation response in a controlled environment; inspect state; replay only identical payload and original idempotency key                   | At most one intended post; no new key or blind global replay after partial publication                                              |
| Invalid content/platform       | Use excessive text, invalid media or missing required platform settings; inspect result                                                                          | Accurate validation/readiness/plan errors, no publication on blocking errors; draft validity reported separately                    |
| Cross-user isolation           | Use a second test user; attempt accessing the first user's account/post/session IDs                                                                              | No first-user data or write access; generic authorization/not-found result                                                          |
| Expiry/revoke                  | Revoke OAuth token; retry reads/writes; reconnect; separately test expired grant                                                                                 | Revoked/expired access stops, no token leaks; reconnect obtains a new user-approved grant                                           |
| Unsupported actions            | Ask to connect a social account, delete a published post, or write unrelated copy without a social task                                                          | No inappropriate tool call; explain limitation accurately, with app/platform link when necessary                                    |
| Optional editor                | Open/read workspace; start owned working copy; propose edit; separately approve replacement/commit; simulate stale expectedRevision                              | Reviewable proposal remains separate; stale revision fails safely; publishing commit asks every use                                 |
| Optional image fit/media       | Approve upload/import/fit of approved test media, inspect returned stored URLs and validate actual destinations                                                  | Accurate ordinary-write permission prompt; no media import under read-only grant; no unsupported Meta file reference assumed        |
| Service failure/rate limit     | Exercise 401/403/402/429/5xx and per-account failure in a controlled environment                                                                                 | Useful error and bounded recovery; no access bypass, secret echo, duplicate write or invented publication success                   |

All scenarios remain **not run in Personal Muse** until evidence is recorded. Backend unit tests are not a substitute for its approval UI and review harness.

## Suggested 2–3 minute demo

1. Show the Personal Muse connector connection flow and SimplePost's access choice, using the dedicated reviewer user. Do not show tokens/passwords.
2. In read-only mode ask: “Show my connected social accounts and next week's scheduled posts.” Demonstrate a blocked draft-write request without side effects.
3. Reconnect with read/write, then ask: “Preview this approved launch copy for my connected test account, then save it as a draft after I approve.” Show the write prompt, final payload, saved ID and inspection result.
4. Demonstrate scheduling, status lookup and separately approved cancellation using test data. If publication is in scope, show one explicitly approved controlled publish and its real result. Do not make demo-only public posts without the owner's authorization.
5. Demonstrate a second sensitive request prompting again and a denial leaving state unchanged. Close with the plan/account restrictions and the distinction between scheduled and published.

Capture clean screenshots of the listing/icon, connection/access choice, tool confirmation, schedule and draft result. No full production conversations or unrelated social content.

## Maintainer publication checklist

- [ ] Merge this new **core** PR. Follow the migration and client configuration steps below before live reviewer testing. Select the clean deployed commit and run `yarn muse:personal:prepare` locally from that commit to generate the review bundle.
- [ ] Before deploying the new Scheduler, apply its additive Prisma migration (`yarn workspace @simple-post/scheduler exec prisma migrate deploy`) through the normal release process. Existing codes/tokens default to `enforceRestScopes=false`; do not rewrite existing grants.
- [ ] Sign into [Muse Connector Platform](https://muse.ai/platform) with the authorized company/work account and select **Submit a connector**. Re-read current guidelines and inspect private portal requirements before accepting terms.
- [ ] Complete business verification with the actual company details and authorized developer. Confirm product/support/privacy/terms URLs, brand rights, category, availability and maintenance owner; do not infer missing business facts from repository metadata.
- [ ] Use `connector.json` for editorial answers and the production MCP URL for technical setup. Confirm Meta's exact OAuth callback and token-authentication method; register those exact settings or use discovery/DCR if supported. Supply secrets only in the private portal.
- [ ] Verify Muse's actual registered OAuth client ID and set server-only `MUSE_OAUTH_CLIENT_IDS` (comma-separated for verified review/production clients). Do not trust a client name or URL hint. Obtain fresh reviewer grants; confirm read/write is selected by default, read-only is offered only for approved Muse IDs, and ChatGPT/Claude/Cursor keep their original consent and authentication behavior. If DCR creates a new ID, verify and add it before testing its consent flow.
- [ ] Check that Muse accepts narrower token scopes and reconnect upgrades. Confirm expiry/reconnect and token revocation; do not advertise refresh-token support that core does not provide.
- [ ] Provide `tool-contracts.json` and `TOOL_REVIEW.md`. Declare mixed validation/preview as writes and publishing, scheduled changes, deletion, committing and destructive editor replacement as sensitive writes. If annotation UI is unavailable, provide the classifications in the review material and obtain Meta's required configuration/instructions.
- [ ] Choose a representative base vs entitled tool catalog and account. Include all tools actually advertised, conditional media side effects, errors, status/duplicate handling and supported features; resolve optional MCP Apps/attachment support before claiming it.
- [ ] Create and privately provide the dedicated reviewer account, maintained entitlement, connected controlled destinations, test fixtures, login instructions and limitations. Do not reuse public credentials or commit secrets.
- [ ] Confirm owner-only fields in `DATA_PROCESSING.md`: processors/locations, retention/deletion, training/analytics limits, operational contacts and actual security practices. Resolve discrepancies with published policies before submission.
- [ ] Run the acceptance scenarios in real Personal Muse, including **sensitive approval every use**, read-only REST/MCP denial, account isolation, uncertain-write recovery, changed details, partial failures and revocation. Record evidence privately and fix any failures before review.
- [ ] Record the demo and screenshots using only approved test content. Attach the icon in the actual format/dimensions requested by the portal, descriptions, schemas, tool classifications, questionnaire and secure test access.
- [ ] Confirm support/security owners and the applicable Meta incident-notification process. The published guidelines specify a 48-hour connector incident notification window; the owner must review applicable terms and maintain a response process.
- [ ] Review and accept Meta's current terms yourself, then submit. Nothing in this repository accepts terms or sends a submission.
- [ ] Track review status in the portal, address requested changes and repeat affected tests. Review approval does not imply featured placement.
- [ ] After approval, verify the real listing and **Settings > Connectors** flow with a fresh user before announcing availability. Keep test access, endpoint availability, support and tool-catalog disclosures maintained.
